# Meal Prep (GAP-49) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record batch-cooked dishes, spend their portions across the meal planner, and keep the remaining-portion count in step with the plan.

**Architecture:** Pure portion arithmetic and Zod schemas in `prepared-batch-calc.ts`; household-scoped Server Actions in a new `prep-actions.ts`; the inventory deduct/credit and preview code that "Mark as cooked" already has is lifted into a shared server module so recording prep reuses it. UI is a new Prep tab plus small additions to the planner, the mark-cooked dialog and the home dashboard. No schema change: `PreparedBatch` and the `MealPlanEntry` link fields already exist (PR #179).

**Tech Stack:** Next.js 16 App Router, React 19, Prisma 7, Zod, Base UI/shadcn, Sonner, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-14-meal-prep-design.md`

## Global Constraints

- Every Server Action starts with `requireHousehold()`; never accept a household id from the client; every Prisma read/write is scoped by household (entries via `mealPlan: { householdId }`, batches via `householdId`).
- Every multi-row write is one `prisma.$transaction`.
- Portion bounds: 1–`MAX_LEFTOVER_SERVINGS` (100) per batch; 1–5 dishes per prep (`MAX_PREP_DISHES = 5`).
- Default eat-by: `cookedAt + LEFTOVERS_SHELF_LIFE_DAYS` (3) days.
- Invariant: `0 ≤ remainingPortions ≤ totalPortions`; a linked entry has `recipeId = batch.recipeId` and `portions = preparedPortionsUsed`; unlinking always resets `preparedBatchId = null, preparedPortionsUsed = 0`.
- Decrement is a conditional `updateMany({ where: { id, householdId, remainingPortions: { gte: n } }, data: { remainingPortions: { decrement: n } } })`; `count === 0` throws inside the transaction → translated `prepNotEnoughPortions` error.
- All user-facing strings in `en.ts` and `sv.ts` under `mealPlanning` (keys prefixed `prep`); errors via `fail("<key>")` in `@/lib/actions/errors` (add keys to the shared error dictionary the same way existing `fail` keys are). No JSX string literals.
- Base UI: `render` prop, never `asChild`. DESIGN.md M1–M10: 44 px targets on touch, steppers not typing for portions, primary action in the thumb zone.
- Tests never hit a DB: mock `@/lib/prisma`, `@/lib/session`, `next/cache`, `@/lib/i18n/get-dictionary` like `cooking-actions.test.ts` does.
- Comment style: explain *why*, at the density of the surrounding file.
- Commit after each task (Conventional Commit, attribution trailer from the session).

## Review Focus

1. **Two people plan from the same batch at once** → the second assign fails with "not enough portions left", never a negative count. Pinned by the conditional `updateMany` test in Task 4.
2. **Plan portions with one slot already holding a different dish** → whole save rejected, nothing written (no partial assign). Task 4 test `rolls back when one slot is taken by another dish`.
3. **Deleting a recipe that has a batch** → the batch cascades away and the planned slot loses both links (`recipeId` and `preparedBatchId` SetNull) but keeps a stale `preparedPortionsUsed`. Expected: the slot still renders as it does today for a deleted recipe, and deleting it later neither throws nor touches another batch. Task 5 test `deleteMealEntryAction tolerates an entry whose batch is gone`.
4. **Undo "Record prep" after a portion was planned** → refused with `prepUndoAlreadyPlanned`, ingredients not credited. Task 3 test.
5. **Marking a prepped slot "Eaten" then deleting it** → portions are *not* returned (they were eaten). Task 5 test `does not return portions for an eaten entry`.

### Task 4: Assign, unassign, discard

**Files:**
- Modify: `src/app/dashboard/meal-planning/prep-actions.ts`, its test, dictionaries.

**Interfaces:**
- Consumes: Task 1 `assignPortionsSchema`, `portionsAfterReturn`, `DiscardSnapshot`, `discardSnapshotSchema`.
- Produces (all return `Promise<ActionState>` unless stated):
  - `assignBatchPortionsAction(input: { batchId: string; slots: { date: string; mealType: MealType; portions: number }[] })` — loads the batch (household-scoped; `prepBatchNotFound`). In one transaction: conditional decrement by `totalRequested(slots)` (see Global Constraints); per slot: upsert the week's `MealPlan` (`getWeekStart` of the slot date), then look for entries in that slot. No entry → create `{ recipeId: batch.recipeId, portions, preparedBatchId, preparedPortionsUsed: portions }`. An unlinked, unconsumed entry with `recipeId === batch.recipeId` → update it to linked with those portions. Any other entry in the slot → throw → `prepSlotTaken`. Export `assignInTx(tx, householdId, batch, slots)` from a non-`"use server"` module (`prep-assign.ts`) because Task 5's `addMealEntryAction` reuses it.
  - `unassignBatchPortionAction(entryId: string)` — entry household-scoped, linked and not consumed; in one transaction: batch `remainingPortions = portionsAfterReturn(...)` (read then `updateMany` scoped by household), entry reset.
  - `discardBatchAction(batchId: string): Promise<ActionState & { snapshot?: DiscardSnapshot }>` — in one transaction: read batch + linked entries, reset those entries' `preparedPortionsUsed` to 0 and `preparedBatchId` to null, delete the batch; return the snapshot.
  - `undoDiscardBatchAction(snapshot: DiscardSnapshot)` — validate; recreate the batch with the same id (only if its recipe is still the household's), re-link the snapshot entries that are still household-scoped and still unlinked.
