## Notes / decisions
- `estimatedPrice` on `ShoppingListItem` has no UI to set it yet anywhere in the app (grep confirms it's only read, never written from a form) — summing it is still correct per the task spec ("only items that actually have one set"), it just means the total will most often be 0 today. Not in scope to add a price-entry UI.
- Treating `estimatedPrice` as already the total for that line item (not per-unit) — consistent with how `togglePurchasedAction` already uses `item.estimatedPrice` directly (unmultiplied by quantity) when writing `PriceHistory`.
- Only create the Transaction when the summed total is > 0 — a $0 expense transaction serves no purpose.
- Not wrapping the status update + transaction create in one `$transaction`, since `findOrCreateGroceriesCategory` takes a plain `prisma` client (not a `tx`) and duplicating its lookup inside a transaction would violate "use Task 2's helper, don't duplicate it". Matches the existing file's style of sequential (non-transactional) find-or-create calls elsewhere (e.g. `addAdHocItemAction`).
- The Browser preview tool's `preview_start` launched its dev server from the main repo's checkout (`C:\Users\ErikHector\Desktop\household-hub`), not this worktree — confirmed via `preview_list`'s `cwd` field. All UI clicks against that server were silently exercising pre-Task-7 code, which is why the first several manual verification attempts showed no `Transaction`/category created. Fixed by starting `next dev -p 3100` manually from this worktree via Bash and pointing the browser at `localhost:3100` instead. Also hit a separate, apparently pre-existing dev-mode hydration mismatch (`ThemeIcon` sun/moon/monitor icon differs between SSR and client, unrelated to this feature) that made `computer` click coordinates land inconsistently after React "regenerated" the tree; worked around it for verification by dispatching `.click()` via `javascript_tool` directly on the located button. Neither issue reflects a problem with the shipped feature code.
- End-to-end manual verification (against the shared dev Postgres, in the "Test Household" household, all rows cleaned up afterward): completing a list with one purchased item at `estimatedPrice: 12.34` created a `BudgetCategory` named "Groceries" (`type: EXPENSE`) and a `Transaction` (`amount: 12.34`, `type: EXPENSE`, `description: From "Shopping list — 2026-09-05"`, `createdByUserId` set) — visible correctly on `/dashboard/budget`'s summary and transaction list. A second run confirmed the toast (`[data-sonner-toast]`) reads "Logged 7.00 to your Groceries budget" for a $7 item. Completing a list with no priced purchased items creates no category/transaction and shows no toast (verified implicitly: the very first test list, with no price set, went to `COMPLETED` with zero budget rows created).
